1
单 terminal fallback 会静默篡改 module 内部语义 错误事件名不报错，反而悄悄修改 module 的 branch 绑定
▶
在哪儿
BuildTransitionVisitor.cs:43-44 FSMDefineBuilder_FluentApi.cs:40-41, 285-286 FSMDemo.API/Services/EngineManager.cs:348-352

4 处 ResolveSourceNodes 都有同一段 fallback。

代码（核心 fallback）
// BuildTransitionVisitor.cs:33-47 if (instance.TerminalNodeNames.Count > 0) { var matchingTerminals = instance.TerminalNodeNames .Where(nodeName => NodeDict.TryGetValue(nodeName, out var node) && FSMNodeBranchEventHelper.PublishesEvent(node, eventName)) .ToList(); if (matchingTerminals.Count > 0) return matchingTerminals; // ↓↓↓ 这里就是问题：terminal 根本没发布 eventName，却照样返回它 if (instance.TerminalNodeNames.Count == 1) return instance.TerminalNodeNames; // 凭空把错误事件名"认领"了 throw new ScriptException(...); }
触发场景演示
📋 场景：module CheckA 有 1 个 terminal 节点，外部连线写错了事件名
CheckA (module, 1 个 terminal: CheckA.Exit)
  CheckA.Exit 的 branch：OK, NG （只发这两个）

外部连线（用户写错了，把 NG 写成 NGG）：
  NGG → CheckA to CheckB.Entry

────────── 引擎实际做了什么 ──────────
1. ExternalEventToInternalNodes["NGG"] → 空（不是 output 映射）
2. PublishesEvent(CheckA.Exit, "NGG") → false（Exit 没这个 branch）
3. fallback：TerminalNodeNames.Count==1，返回 [CheckA.Exit]
4. EnsurePublishesEvent 发现 Exit 是单分支可绑 → 强行把 NGG 塞进 Exit 的 branch！

结果：用户拼错的事件名 NGG 被静默接上了，还顺手改了 module 内部的 Exit。
没有报错，没有警告，运行时表现诡异（Exit 现在发 OK/NG/NGG 三个）。
🔧 建议：改 throw（不破坏正常用法）

正常用 output 映射或正确事件名时根本走不到这个 fallback。能走到这里的，几乎都是用户写错了。把 if (Count == 1) return ... 改成 throw new ScriptException("module X 的 terminal 节点未发布事件 Y")，让错误在构建期就暴露。改动小（4 处），回归风险低（Test 1-9 不触发此分支）。

2
output 映射值与内部事件名碰撞 → 跨边界联动 两个本该独立的事件被合并成一个，内外互相触发
▶
在哪儿
BuildStateVisitor.cs:678-693（Phase 3 事件展开） FSMDefineBuilder_FluentApi.cs:469-484

所有事件（内部 + 外部映射）共用同一个 EventDict，按字符串 key 合并。

根因
// BuildStateVisitor.cs:680-693 foreach (var kvp in template.TemplateEvents) { var eventName = kvp.Key; if (template.Outputs.Contains(eventName) && currentOutputMap.TryGetValue(eventName, out var mappedEvent)) { // mappedEvent 是用户写的外部事件名 if (!EventDict.ContainsKey(mappedEvent)) EventDict.Add(mappedEvent, new FSMEvent(mappedEvent)); } else { var newEventName = currentModulePrefix + eventName; // e.g. "Sub1.Next" if (!EventDict.ContainsKey(newEventName)) EventDict.Add(newEventName, new FSMEvent(newEventName)); } } // 如果 mappedEvent == "Sub1.Next"（正好等于某个内部事件全名） // 两者会合并成同一个 FSMEvent 实例 → 内外共享触发
触发场景演示
📋 场景：用户在 output map 里写了一个恰好等于内部事件全名的值
module Sub1：
  内部节点 Sub1.Work 发布内部事件 Next
  （展开后全名 = Sub1.Next）

实例 body：
  output Out → "Sub1.Next" // 用户想映射到外部，但名字撞了

────────── 引擎实际做了什么 ──────────
EventDict 里只有一个 "Sub1.Next" FSMEvent 实例，被两个地方引用：
  • module 内部转移：Sub1.Work --Sub1.Next--> Sub1.End
  • 外部转移：外部节点 --Sub1.Next--> 某个 target

结果：Sub1.Work 触发时，外部那条转移也跟着激活；
反过来，外部触发该事件也会激活内部转移。
两个本该独立的子图被悄悄连起来了。无报错，难排查。
🔧 建议：展开时加碰撞检测

在 Phase 3 展开 output 映射事件时，检查 mappedEvent 是否等于 currentModulePrefix + 任一内部事件名，若冲突则 throw。触发条件需要用户主动构造碰撞名（罕见），但碰撞后果完全静默，值得加防护。改动集中在 BuildStateVisitor 和 FSMDefineBuilder 的展开循环。

3
input ∩ terminal 节点可能产生自环 transition 同一节点既是入口又是出口，代码没有互斥校验
▶
在哪儿
BuildStateVisitor.cs:670-673（标记 input/terminal，无交叉检查） BuildTransitionVisitor.cs:107-134（连线，无 source==target 检查）
为什么是问题

语义上 input（模块入口）和 terminal（模块出口）是互斥概念。但声明期（VisitInput_declaration / VisitTerminal_declaration）和展开期（670-673）都没有交叉校验，允许同一节点身兼两职。

触发场景演示
📋 场景：节点 X 同时声明为 input 和 terminal
module M：
  input X
  terminal X // 同一个 X
  X 的 branch 发布 output Out

实例 Sub1，output Out → EventA
外部连线：EventA → Sub1 to Target

────────── 引擎实际做了什么 ──────────
ResolveSourceNodes("EventA") → 经 ExternalEventToInternalNodes → [Sub1.X]
ResolveTargetNodes("Sub1") → 经 InputNodeNames → [Sub1.X]

创建转移：Sub1.X --EventA--> Sub1.X （自环，合法通过）

结果：逻辑上荒谬的自环被允许创建。
🔍 建议：声明期加 input/terminal 互斥校验

触发条件较刻意（用户得主动把同一节点声明两次），实际脚里很少见。但 input/terminal 互斥是基本语义，应在声明期（VisitTerminal_declaration）就校验，而不是等连线时产生诡异自环。改动小，回归风险低。

4
多节点发布同一 output → fan-out 行为未文档化 行为本身合理，但代码里没写清楚这是预期的
▶
在哪儿
BuildStateVisitor.cs:820-822（去重只按节点名） BuildTransitionVisitor.cs:27-31（整表返回）
行为
📋 场景：module 内两个节点都发布同一 output
module M：
  Check1 branch 发布 Out
  Check2 branch 也发布 Out

实例 Sub1，output Out → EventA
外部连线：EventA → Sub1 to Target

────────── 引擎实际做了什么 ──────────
ExternalEventToInternalNodes["EventA"] = [Sub1.Check1, Sub1.Check2]
创建 两条 transition：
  • Sub1.Check1 --EventA--> Target
  • Sub1.Check2 --EventA--> Target

结果：fan-out 到所有发布者。
这其实是合理的 —— 比如"两个检查节点任一发 NG 都跳到同一目标"是常见设计。
📝 建议：在 CONTEXT.md / ADR 里写明 fan-out 语义

行为本身不是 bug。"两个检查节点都发 NG"是合理设计。但代码里没有任何注释说明这是预期，未来维护者（或下次的我）可能误以为是 bug 想去"修复"成单发布者。建议在 archive/CONTEXT.md 的 module 术语条目里加一句"output 可多发布者，外部连线 fan-out 到全部"。

是不是 bug？

大概率不是。"Transform"（变换/重构）这个名字本身暗示"重新接线"，Force 语义（ForceConnectNode 在重复时删旧重连）像是给"运行期重连"留的口子。但 IFSMTransformBuilder 接口没有任何 XML 注释说明这点，用户用 TransformFSMDefine 时容易意外丢失旧连线。

📝 建议：给 IFSMTransformBuilder 加 XML 注释

在 IFSMTransformBuilder 接口和 TransformFSMDefine 方法上加 <summary> 注释，明确写"当 (source, event) 已存在时，会静默覆盖既有 transition（删除旧的、接上新的）。如需严格模式请用 ConfigureFSMDefine"。不改行为，只补文档。需要你确认 Force 语义是否真是设计意图。

审计方法：通读 BuildStateVisitor.cs、BuildTransitionVisitor.cs、FSMDefineBuilder_FluentApi.cs、FSMExecutor.cs、FSMEngine_Function.cs，针对 module 展开 / output 映射 / 连线解析 / 事件字典合并等关键路径提出 5 个假设，逐个在代码里验证。已通过 FSMScriptAnalyzerTest Test 1-9 确认现有脚本不受影响。

与刚才 rename 工作的关系：本报告所有发现都在核心库 StateMachine/，与 FSMDemo.API 编辑层的 rename / output map 编辑无关。两者是独立的语义层。
